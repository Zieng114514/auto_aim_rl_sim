## 2. 两个真 bug（都是这次为了跑训练才暴露的）

### 2.1 合并 XML 的竞态：xml_hook 分支在**锁外原地重写**

* 报错：8 个 worker 同时起 → `ValueError: XML parse error 7 ... XMLElement name=joint`
  （`MjModel.from_xml_path` 读到写了一半的文件）。
* 真因**不是** `merge_real_assets`（那部分早就加了 flock + 原子替换），而是
  `Demo.__init__` 里 `xml_hook` 分支：`open(merged, "w").write(xml)` —— 原地截断重写，
  无锁、非原子。而 RL env 恰好传了 `xml_hook`（rm_link 那套材质/伺服/相机改写），
  所以只有 RL 训练会踩到；之前"substring not found"那个怪错也是同一类。
* 修法（`rm_sim/rm_gimbal_demo.py`）：
  1) 新增 `write_merged_atomic()`：**所有**写合并 XML 的路径统一走它（锁内写、`os.replace` 原子替换）；
  2) 文件名带**内容指纹** `rm_demo_merged_<sha1_12>.xml`：不同配置（`--cars`/贴纸/dt）
     互不覆盖，同配置多进程共享同一份（内容一致，谁写都一样）；另存一份稳定名快照供人看；
     自动清理旧指纹文件（留最近 6 份）；
  3) `xml_hook` 收进 `merge_real_assets(..., xml_hook)`，在锁内生效；
  4) 地形 PNG 也顺手修了：原来**每次构建都重写** `~/.cache/rm_gimbal_demo/terrain.png`，
     多个进程同时写+读同样会读坏 → 改成"存在就跳过 + 临时文件 + 原子替换"。
* 验证：新增探针 `scratch/probe_merge_race.py`（A=并发 merge+load，B=并发整世界，
  H=**带 xml_hook** 的并发 merge+load 各 5 轮 × 8 进程）→ 全绿。

### 2.2 观测 12/13/14 维是**死特征**（恒等于 0）

`sim_env.step()` 里先 `self._last_aim_err = 本周期误差`、`self._last_cmd = 本周期指令`，
**然后**才调 `_obs()` —— 于是"误差变化率 / 指令变化率"三项永远是 0。
训练能跑，但策略拿不到"云台还在晃、别开火"这类信息。

* 修法：把 last_* 的更新挪到 `_obs()` **之后**；`reset()` 里用当前真值初始化 last_*，
  避免首帧凭空跳一下。已加回归断言到 `auto_aim_rl/env/test_env.py`（std 必须 > 0）。
* 影响：已跑/正在跑的旧训练作废（20k 步的 `policy.pt` 只当**联调样本**用，不作为结果）。

## 8. 又抓到一个"假可复现"：枪的随机源没跟 seed 绑定

## 10. 续：PPO 冷启动"越练越差" → 上行为克隆预热 + KL 早停

**现象**：`stage1_a` 冷启动跑下来，平均回报从 22.5 单调掉到 19.2（upd 40），
镜像环境里 checkpoint 命中率 36.4% → 33.3% —— **练得越久越差**。

**两个原因**（都改了）：

1. **PPO 过拟合一轮 rollout**：6 epoch × 4 minibatch = 24 次梯度，没有 KL 早停。
   现在加 `--target-kl 0.02`（超过 1.5× 就停这一轮），学习率 3e-4 → **1e-4**。
2. **奖励极稀疏**：每步只有 ~2.5% 是"开火"，冷启动要先学会"什么时候该开火"
   这件本来就有人会做的事 —— 于是按 DESIGN.md §3.0.2 的预案加了
   **行为克隆预热**（`train/bc_warmstart.py`）：用镜像的经典门限策略跑若干回合，
   记录 (观测, 动作) 做加权交叉熵，存成与 ppo.py 同样格式的 `policy.pt`，
   再 `--init-from bc.pt` 接着练。

**BC 的类别权重很关键**（实测，镜像环境 3 回合 × 90 s）：

| 权重 | 与老师一致率 | 学生开火率(老师 15.4%) | 闭环命中率 |
|---|---|---|---|
| none | 85.5% | 8.9% | **0%（几乎不开火）** |
| sqrt | 84.2% | 21.5% | **47.1%（但只打了 34 发，太保守）** |
| balanced | 80.5% | 30.3% | （开火过多，未测闭环） |

结论：**"一致率"不是指标，闭环命中率×射频才是**（sqrt 的命中率漂亮但弹量只有
老师的 1/3，TTK 一定差）。下一步用 sqrt 权重初始化 + PPO 微调，让策略自己把
"该多打的时候多打"学回来。

## 12. 首次 C++ 闭环对照（stage2，3 种子 × 300 s，同机背靠背）

| 指标 | rl_stage2（BC+PPO） | sp_vision_v3（规则） | 胜者 |
|---|---|---|---|
| 命中率 | 26.1%（704 发 184 中） | **27.3%**（765 发 209 中） | 规则 |
| 击杀台数 | 4 | **6** | 规则 |
| 每击杀弹量 | 176 | **128** | 规则 |
| TTK(首中→death) | **114.0 s** | 138.4 s | RL |
| 过热被拒 | 16884 | 1146 | —— |

分靶型：RL 在 **3/4 类**上命中率更高（原地甩头 51.0% vs 49.5%、急停冲刺 38.6% vs 37.1%、
随机旋转移动 10.2% vs 5.9%），但在"固定周期旋转移动"上明显更低（7.7% vs 12.6%），
且**在两类移动靶上多打了 62 发**（258 vs 196）—— 热量被浪费在低概率时机上。

### 12.1 根因：奖励把策略训成了"热量一好就开火"

C++ 日志里 `过热被拒 16884 次`（规则策略只有 1146 次）说明策略在**持续请求开火**；
镜像环境里直接量到：**开火请求占 73.8% 的决策步**，热量长期停在 0.92~0.99。

原因是奖励 `hits - c_fire × shots` 里 `c_fire = 0.10`：只要"这一发的命中概率 > 10%"
就值得打。而实测各靶型的命中概率是：原地甩头 50%、急停冲刺 38%、两类移动靶 6~10%
—— 于是"能打就打"成了最优策略，热量全花在移动靶上。

**这件事在热量模型下是有明确最优解的**：热量上限 100、回热 10/s（≈1 发/s），
靶型每 10 s 一换。在移动靶段（P≈8%）**攒热量**，留给下一段原地甩头（P≈50%）
爆发，同样的热量能多换 5~6 倍的命中。所以把 `c_fire` 提到 **0.25**
（= 只有 P(命中) > 25% 才值得开火）应当**同时**改善命中率和击杀时间 ——
`stage3_heat` 正在按这个配置训练（`ppo.py --c-fire 0.25`，已加 CLI）。

## 13. 部署侧的观测校验（这一步救了命）

给 `ShooterRL` 加了"头 3 帧打印整条观测 + 每 300 次打印摘要"，再配
`scratch/dump_obs.py` 打训练侧分布，逐维对照。结果抓到一个**真 bug**：

* `ey = command.yaw - gimbal_pos[0]`：两边各自都在 [-π,π] 内（eulers 内部做过 limit_rad），
  跨 ±π 边界直接相减会蹦出 **±2π 的尖峰**（日志实测 `ey=-6.10`，≈ -350°）。
  这种值训练时从未出现过 —— 属于把策略推到分布外。已在 C++ 与 Python env 两侧
  统一绕回 `(-π, π]`。
* 其余维度对得上：`dist/5≈0.4~0.6`、`ep≈-0.44`（含炮管 25° 安装角，
  两边同口径）、`seen=1`、`valid=1`、`heat` 长期 0.9+。

**教训**：`ONNX 能加载、程序不崩` 完全不等于`部署正确`。观测必须逐维对分布，
否则策略表现成"不响应"，从命中率上根本查不出来。

2. **镜像里的 ThresholdPolicy 早就跑不了了**：删掉"回合进度"那一维后
   瞄准点有效从 `obs[21]` 变成 `obs[20]`，`policies.py` 没跟着改
   → 21 维观测下直接 IndexError（"33.3% vs 34.4%" 那个环境可信度结论是 22 维时代测的）。
   修好后重测：**镜像 37.1% vs C++ 34.4%**，环境可信度结论依然成立。

## 16. 续：把 c_block 试了一遍 —— 结论是"太粗"，会训崩

按 §12.1 的分析给奖励加了 `c_block`（被锁枪挡下的开火请求的代价，默认 0）：
因为"被挡是免费的"⇒ 最优解退化成"一直请求"（实测请求占 74% 决策步），
策略学不会挑时机。实测（`stage4_select`，`--c-fire 0.10 --c-block 0.005`）：

* 镜像里确实变好了：同弹量（396 发）命中率 **32.1% → 33.6%**，击杀 2 → 3；
* 但**训练信号崩了**：平均回报从 +23 掉到 **-17.8**（随机采样探索时被挡的请求太多，
  惩罚压过命中收益），策略在"干脆不开火"（回报 ≈ 0）与"开火"之间被推向后者不划算的一侧。
* 落盘的 checkpoint 本身还能用（argmax 推理、无域随机化时 34.8%），
  说明**训练回报崩 ≠ 策略坏** —— 但用这种信号继续练没有意义。

**正确的做法（写进待办）**：惩罚"热量顶到上限"的步数（= 浪费回热），
而不是惩罚被挡的请求。这样"这一格热量现在花掉还是等 0.2 s 打更有把握的一发"
才成为真正的决策；现在只能说是"试过、方向对、实现太粗"。

## 17. 续：评测协议加限速（`sim.main_fps`）

帧率-命中率强相关（§14）让所有跨运行的比较都不干净。给 sim_main 加了主循环限速
（`configs/sim.yaml` 的 `sim.main_fps: 20`，0 = 不限），把每个周期对齐到固定节拍。
好处有两个：**两个策略的帧率被钉在同一个值**；而且限速后循环有余量，
机器被轻度占用也不会再污染结果（实测限速后 19.4~21.6 FPS，

## 19. 续：按"热量浪费感知"改奖励 —— 结果是"过度保守"

奖励改成 `c_fire=0.22 + c_waste=0.03`（`stage5_sched`，400k 步，`--ent-coef 0.003`）：

* 训练回报稳定在 +11~16（没有再崩），说明 `c_waste` 确实挡住了"干脆不开火"的退化；
* 但镜像里射频掉到 **0.26 发/s**（规则门限 1.1 发/s）、命中率 32.6%、**0 击杀** ——
  热量根本没被用掉，"择时"变成了"不打"。
* 中途 checkpoint（143k 步）的 C++ 闭环更差：**17.5%**（同种子规则门限 25.8%）。

**规律**：`c_fire` 是给"一发弹"定价。定价低于平均命中概率 → spam；
高于它 → 干脆不打。三种配置（0.10 / 0.22 / 0.25）分别落在 spam / 保守 / 保守，
**问题不在具体数值，而在于用"固定单价"去近似"热量的影子价格"**。

## 20. 挖到根子上：镜像的跟踪质量比 C++ 干净一个量级（本次最重要的发现）

给 `sim_main` 加了 `[Aim]` 行（每秒打印 |ey|/|ep| 的中位与 p95，纯几何量、与策略无关），
和镜像侧的 obs[10] 分布一比：

| | 镜像（训练用） | C++（实测） |
|---|---|---|
| \|ey\| 中位 | ~0.003 rad | **1.2~1.9°（0.021~0.033 rad）** |
| \|ey\| p95 | 0.031 rad（1.8°） | **2.8~5.9°（0.049~0.103 rad）** |

**镜像的 95 分位只等于 C++ 的中位**。后果不是"命中率乐观几个点"，而是
**策略排序反转**：stage5（学"什么时候算跟稳了"）镜像 36.9% → C++ 17.5%；
而规则门限镜像 38.7% → C++ 32.4%。选择性策略学到的是**镜像特有的干净信号**。

试过用噪声把镜像调"脏"（`scratch/calib_mirror*.py`）：位置噪声 0.9°/延迟 60ms
→ 镜像 26.4%（\|ey\| 中位 0.90°/p95 2.71°）；再往上（1.35°/1.8°）命中率掉到 21.4%/14.2%。
**C++ 是"误差尾部更肥、但同样误差下更容易中"** —— 说明偏差在"瞄准点→命中"这一段
（C++ 的 pitch_offset/延时是在 C++ 里标定的），**只调跟踪噪声调不平**。

**下一步（写进 agnet.md §6 待办，最高优先级）**：用**逐发弹道偏移分布**标定镜像 ——
两边都记了 `shot_log` 的 off_v/off_h/off_n（连续量，几十发就能对齐），
把镜像的瞄准/弹道模型对到 C++ 的实测分布上；**标定之前继续训 RL 没有意义**。

## 22. **突破：学习型门限四项指标全面超过 sp_vision**（2026-10-14）

### 22.1 做法：在闭环里学"这一发值不值得打"，再拿它当门限

`rl_shooter_mode: quality`：用闭环采集的真实数据训练 P(命中|观测)（16 维特征，
**刻意不含热量/计时器/最近命中率**），部署规则就一条：

    fire = (p >= λ) && 瞄准点有效

### 22.2 三个把这条路走通的坑（都记在代码注释里了）

1. **不能把"最近 10 发命中率"喂进质量模型**：它是策略自己行为的函数 ——
   门限一收紧、几发没中，"最近命中率"就掉到 0，模型据此判断"现在不好打"，
   于是更不开火，**自锁死循环**（实测 λ=0.69 时放行率只有 0.4%，远低于离线预期的 10%）。
2. **热量的物理是"漏桶"不是"充电宝"**：`rm_gun` 的热量从 0 开始、只随开火增加、
   以 10/s 衰减 —— **攒不了热量**（我一度按"可以在难打的靶型段攒热量、留给好打的段爆发"
   设计，日志里 heat 中位数 0.00 才发现根本不成立）。所以"选择性开火"的收益来自
   **在同一秒内的 20 个决策格里挑最值得打的那一格**，而不是跨时段的预算调度。
3. **λ 必须按闭环里真实的 p 分布来选**，不能用离线数据的分位数：离线 top-10% ≈ 0.73，
   闭环里同一个 λ 可能只放行 0.4%。已把每帧的 (p, heat, fire, valid) 落盘
   （`rl_shooter_log_path`），标定 λ 只看这份数据。

## 21. 换打法：在 C++ 闭环里直接采数据（stage 2 监督学习），并补上镜像的"瞄车心"坑

### 21.1 镜像的第一处修复：瞄的是车心，不是**转动中的装甲板**

真 Aimer 的 `choose_aim_point()` 选"最正对射手的那块板"，瞄的是**板心**。车辆自转
7 rad/s 时板心在 0.25 m 半径上扫过，视线角速度 ~25°/s，云台必然滞后 ——
C++ 实测 |ey| 分位 0.48/1.29/**3.13**/6.10/9.37/**12.11** 度；镜像原来瞄"车心"
（自转时几乎不动），|ey| 只有 **0.70°/p95 2.07°**，策略于是学成"什么时候都能打"。
已改成"预测到弹丸飞到时刻的板心 + 锁板滞回"（`mirror.py:MirrorAimer._pick_plate`），
镜像 |ey| 中位升到 0.94°、p95 4.58°（仍不到 C++ 量级：那 3° 主要是
**跟踪器逐帧抖动 → 指令跳 → 云台追不上**的瞬态，手工建模很难完全复刻）。

### 21.2 于是换打法：数据直接在 C++ 闭环里采

新增 `rl_shooter_mode: log` —— 射手在闭环里**放开打**，把每一发真打出去的弹的
"21 维观测 + 中没中"写成 CSV；`train/fit_trigger.py` 拟合 P(命中|观测) 的逻辑回归，
`rl_shooter_mode: classifier` 把概率当门限部署。**这条链路没有镜像→C++ 的迁移损失。**

* 采集 3 种子 × 300 s = **895 发**真实样本（总体命中率 28.7%）；
* 拟合 AUC **0.747**（按时间切分留出验证）；
* 权重里最有信息量的是 **|ey|×距离**（板上横向误差）与 **|指令变化率|**，符合物理直觉。

### 21.3 本轮**最大的单项收益**：pitch_offset 标定过时了

上一轮 1.8° 的标定是在"没有枪模型、没有限速"的老配置下做的。枪模型把实际弹速
从 22 提到 ~24 m/s，弹道整体偏高（off_v 均值 **+35.5 mm**，而装甲板半高只有 28 mm）。
按连续量重扫（同种子 150 s，规则门限，限速 20 FPS）：

| pitch_offset | 命中率 | off_v 均值 |
|---|---|---|
| 1.8（旧值） | 25.8% | +35.5 mm |
| 1.5 | 30.7% | +44.8 mm |
| 1.2 | 39.5% | +22.6 mm |
| **1.0（新值）** | **3 种子 38.3%** | —— |

**重新标定瞄具：命中率 25.8% → 38.3%（+12.5 点）** —— 比这一整轮所有奖励/门限的
折腾加起来都值钱。再次印证 README §5.1：**调瞄具要用逐发偏移这种连续量，别用命中率。**

### 21.4 关键结论：开火时机已经在"平台"上了

用 895 发真实数据算 (命中率 × 射频) 前沿：

| 按预测概率取前 | 命中率 | 折合射频 | 命中/秒 |
|---|---|---|---|
| 10% | **58.4%** | 0.10 发/s | 0.058 |
| 25% | 53.8% | 0.25 | 0.135 |
| 40% | 48.6% | 0.40 | 0.194 |
| 55% | 42.1% | 0.55 | 0.232 |
| 70% | 37.1% | 0.70 | 0.260 |
| 100%（放开打） | 28.7% | 0.99 | **0.284** |

**命中/秒在整条前沿上几乎是常数（0.23~0.28）**：想提高命中率就得降射频，两者对冲。
手工门限（0.61 发/s、38.3%）也正好落在这条前沿上 —— 说明**"何时开火"已经被规则门限
吃干净了**，学出来的逻辑回归在同等射频下并不占优（0.70 发/s 处 37.1% vs 门限 38.3%）。
**真正的瓶颈是瞄准质量（弹道系统偏差 + 跟踪滞后），不是开火时机。**

## 14. 本机评测的帧率-命中率关系（重要）

同一份规则策略、同一批种子，**帧率越高命中率越高**（aimer 用实测耗时做延迟补偿）：

| 种子 | 帧率 | 命中率 | TTK(首中→death) |
|---|---|---|---|
| 12345 | 28.3 | 34.5% | 71.7 s |
| 42 | 27.6 | 23.5% | 131.0 s |
| 20251012 | 22.1 | 22.7% | 138.4 s |

所以：**对比实验必须记录帧率**（已加进 bench_ttk/aggregate），帧率相差 >10% 的结果
不能直接比；理想是把两个策略背靠背跑在同一段机器状态里（本轮 RL 与规则就是背靠背，
但帧率仍有 21.2~26.6 的抖动，这给 TTK/命中率的结论带来不确定性 —— 如实记录）。
